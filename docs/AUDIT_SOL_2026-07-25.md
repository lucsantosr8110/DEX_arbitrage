## 1. ALTO — `executeDirect` ERC20 absorve perda silenciosamente

`FlashloanExecutor.sol:301-308`

```solidity
} else {
    // ERC20: devolve capital + lucro
    if (finalAmount > amount) {
        profit = finalAmount - amount;
        totalProfit += profit;
    }
    IERC20(asset).safeTransfer(msg.sender, finalAmount);
}
```

Caminho nativo exige `delta >= amount` (reverte em perda). Caminho ERC20 **não exige** `finalAmount >= amount`. Arbitragem lucrativa parcial transfere `finalAmount < amount` e o executor come a perda sem revert. Inconsistente com o caminho nativo e com `executeOperation` (que exige `finalAmount >= totalOwed`).

**Cenário:** executor autorizado rota inviável, swaps drenam parte do capital, tx confirma, capital some.

**Fix:**
```solidity
require(finalAmount >= amount, "Cycle did not return capital");
```

## 2. ALTO — `executeOperation` não valida steps

`FlashloanExecutor.sol:318-364`

Callback decodifica `steps` de `params` e chama `this._executeArbitrage` **direto**, sem `_validateSteps`. Pela via `FlashloanCaller.triggerFlashloan`, `params` é caller-controlado (owner do Caller). `executeFlashloan` e `executeDirect` validam; o callback não.

`_executeArbitrage` checa só `currentToken == step.tokenIn` e ciclo fechado — não checa `MAX_STEPS`, não checa `amountOutMin > 0`, não checa tokens zero de forma robusta.

**Cenário:** caller (Caller owner) envia `steps` enorme → loop sem limite → OOG, ou steps com `amountOutMin = 0` → sem proteção de slippage no callback.

Risco atenuado: caller precisa ser owner do Caller (confiança). Mas quebra a defesa em profundidade e diverge dos outros dois entrypoints.

**Fix:** chamar `_validateSteps(steps, asset)` (adaptar para `memory`) antes de `_executeArbitrage` no callback.

## 3. MÉDIO — `executeOperation` ignora `paused`

`FlashloanExecutor.sol:324` — modificador só `nonReentrant`, sem `whenNotPaused`.

`emergencyStop` só bloqueia `executeFlashloan`/`executeDirect`. Mas um initiator autorizado (ex.: FlashloanCaller como `wrapperAddress` ou em `authorizedWrappers`) dispara `flashLoanSimple` direto na Aave — Aave chama o callback — `paused` ignorado.

**Cenário:** owner aciona `emergencyStop` achando que parou tudo; FlashloanCaller ainda dispara flashloan via Aave, callback roda.

**Fix:** adicionar `whenNotPaused` ao `executeOperation` (mas notar que Aave v3 reverte callback se receiver não pagar — então `paused` no callback reverte o flashloan inteiro, que é o desejado). Alternativa: FlashloanCaller checar `executor.paused` antes de disparar.

---

## 4. MÉDIO — `_executeArbitrage` desnecessariamente `external`

`FlashloanExecutor.sol:369-395`

Declarado `external` só para poder envolver em try-catch (comentário). Mas try-catch **foi removido** (`executeOperation` não usa mais — reverte direto). Agora é só chamada `this._executeArbitrage(...)` = external self-call = custo de gas extra + salta fronteira de chamada + mantém função pública exposta (guardada por `msg.sender == address(this)`).

**Fix:** tornar `internal`, chamar direto `_executeArbitrage(...)`. Remove external self-call. Reentrancy mantida (chamada internal não solta `nonReentrant`). Se precisar de try-catch no futuro, usar wrapper interno com flag.

## 5. MÉDIO — Slippage real controlado pelo caller

`FlashloanExecutor.sol:474-481`, `_validateSteps:514`

`updateSlippageConfig` limita `max <= MAX_SLIPPAGE_BPS` (5%), mas **`baseSlippage` sem teto** e `amountOutMin` é caller-supplied. Se `baseSlippage = 0` ou `amountOutMin = 1`, `minReturn` efetivo ~ 1 wei → sem proteção de slippage.

`_validateSteps` só exige `amountOutMin > 0` (1 wei passa). Quem cria os steps (off-chain, executor autorizado) define a proteção real. Slippage config é redução adicional, não floor.

**Cenário:** executor autorizado comprometido ou bug no bot envia `amountOutMin` baixo → sandwich MEV drena.

**Fix:** floor mínimo de `amountOutMin` relativo a valor de entrada, ou rejeitar `baseSlippage == 0` quando `enabled`. Documentar que a proteção de slippage mora no caller.

## 6. BAIXO — Centralização

- `owner` único, `immutable` no Caller e definido no constructor do Executor. Sem `transferOwnership`, sem 2-step, sem timelock.
- `updateExecutor`, `setWrapper`, `authorizeWrapper`, `withdrawToken`, `withdrawMATIC`, `emergencyStop` — tudo `onlyOwner`.
- Sem renounce.

Risco: chave owner comprometida = dreno total (`withdrawToken`/`withdrawMATIC`) + redirecionar executor/wrapper.

**Fix:** AccessControl com roles + timelock; ou multisig no owner. Mínimo: `withdraw` com limite/pausa.

---

## 7. BAIXO — `totalProfit` mistura unidades

`executeDirect` nativo soma `profit` em WMATIC-units; ERC20 soma em asset-units; `executeOperation` soma em asset-units. `getMetrics` retorna número sem unidade — comparar cross-asset é inválido.

**Fix:** métricas separadas por asset, ou normalizar em USD-oracle. No mínimo documentar.

---

## 8. BAIXO — Caller repassa `params` sem sanear

`FlashloanCaller.sol:51-69`

`triggerFlashloan(asset, amount, params)` só valida `asset != 0`, `amount > 0`, `executor != 0`. `params` vai cru pro Aave. Dono do Caller controla conteúdo (vira `executorAddr` + `steps` no callback). Como owner do Caller = quem deployou, é confiança única. Mas acopla segurança do Executor à segurança do Caller.

**Fix:** Caller não deveria formar `params` arbitrário; idealmente Executor expõe `executeFlashloan` e o Caller só repassa asset/amount, com Executor montando `params`. Ou Caller valida hash/estrutura de `params`.
